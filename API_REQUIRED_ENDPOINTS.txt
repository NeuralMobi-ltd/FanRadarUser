FanRadar Required API Endpoints (DETAIL VERSION)
Base URL: http://127.0.0.1:8000
NOTE: /api/Y/users/profile (GET + POST) intentionally excluded (already integrated).

Common Objects (aligned to current frontend store mappings):
UserSummary: { id, username, first_name?, last_name?, profile_image_url?, avatar?, is_following?, followers_count?, following_count? }
Post: {
  id,
  author: { id?, name, avatar },
  content,                 // store maps to 'text'
  media: [ { url, type? } | url ],
  tags: [string],
  fandom?: { id?, name },
  likes: number,
  comments: number,
  isLiked: boolean,
  trending?: boolean,
  createdAt: ISO8601 string
}
Category: { id, name, slug, description?, icon? }
Fandom: { id, name, handle, description?, cover_image_url?, logo_url?, members_count, posts_count, categories:[Category], is_member?, role?, created_at }
Notification: { id, type, data:object, read:boolean, read_at?, created_at }
Product: { id, name, description?, price, currency, images:[url], brand, category, stock, attributes?:object, rating?:number }
CartItem: { id, product:Product(minimal), quantity, unit_price, total_price, options?:{ size?, color? } }
Order: { id, status, items:[CartItem], subtotal, shipping, total, currency, created_at }

Auth Header (when required): Authorization: Bearer <token>
Pagination (when present): query params ?page=<int>&limit=<int>; response: { data:[...], meta:{ page, limit, total, last_page } }

POST /api/users/:userId/follow
  Auth: required
  Purpose: Toggle follow/unfollow target user OR perform explicit action when body.action supplied.
  Id Path Param: :userId (integer | username/slug if backend supports; MUST 404 if target not found or equals auth user when self-follow disallowed).
  Body (optional JSON): { action:"follow"|"unfollow" }
    If body omitted => implicit toggle (follow if not following, else unfollow).
    If body provided => perform explicit action (idempotent: repeating same action returns 200 with current state, not error).
  Headers: Authorization: Bearer <token>
  Rate Limit (recommendation): Max 10 follow/unfollow operations per 10 seconds per auth user to mitigate abuse (429 on exceed).
  Responses:
    200 Follow executed (implicit or explicit):
      {
        "message": "Followed user.",
        "following": true,            // now following = relationship exists
        "follower_count": 121,        // updated follower count of TARGET user
        "following_count": 56         // (optional) updated following count of AUTH user
      }
    200 Unfollow executed:
      {
        "message": "Unfollowed user.",
        "following": false,
        "follower_count": 120,
        "following_count": 55         // optional if you return it above
      }
    200 Idempotent explicit action (already in desired state):
      {
        "message": "Already following.", // or "Already not following." for unfollow
        "following": true,
        "follower_count": 121,
        "following_count": 56
      }
    400 Invalid action value (when provided): { message:"Invalid action" }
    401 Unauthenticated: { message:"Unauthenticated" }
    403 Forbidden (attempt to follow self if disallowed): { message:"Cannot follow self" }
    404 Target not found: { message:"Resource not found" }
    429 Rate limited: { message:"Too many requests" }
  Notes:
    - Ensure atomic update to avoid race conditions causing incorrect counts.
    - follower_count reflects target user's followers AFTER operation.
    - following_count (if returned) reflects auth user's following AFTER operation.
    - Always return both counts or document omission (frontend uses when present, falls back to manual +/- otherwise).
    - Backend should ignore unknown extra fields in body.
  Curl Examples:
    (Implicit toggle) curl -X POST -H "Authorization: Bearer <TOKEN>" http://127.0.0.1:8000/api/users/42/follow
    (Explicit) curl -X POST -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" -d '{"action":"unfollow"}' http://127.0.0.1:8000/api/users/42/follow
  Frontend Expectation: uses following boolean & counts to optimistically update UI; message optional for user feedback.

====================
FRONTEND STORE MODULE REQUIREMENTS (Contracts Backend Must Support)
====================
All stores expect stable IDs (integers) and ISO 8601 timestamps. Nullables should be null (NOT omitted) when absent.

auth store (already working)
  Needs: After login/register, user object with: { id, username, first_name, last_name, email, profile_image (path), background_image (path|null), date_naissance, preferred_categories:[id|name], stats?:{ followers, following, posts } }
  Token: string (JWT or opaque). If exp exists, include exp (unix ts) so we can auto-logout.

categories store
  Endpoint: GET /api/categories
  Response array stable order (used for preferred_categories ID mapping). Each: { id, name, slug, description?, icon? }
  Changes: If order can change, provide explicit id usage only; we will stop using positional index.

posts/news store (home/explore/trending/saved)
  Feed endpoints MUST return { posts:[Post], meta? }
  Required Post fields for mapping: id, author.name, author.avatar, content, createdAt, likes, comments, isLiked, trending?
  Media accepted as array of URLs OR objects { url, type }
  Like toggle: backend returns { liked, isLiked, likes }
  New comment: { id, author, content, createdAt }

user relationships store (followers/following)
  Endpoints: /api/users/:id/followers, /following, follow toggle
  Each user summary must include: id, username, first_name, last_name, profile_image_url, is_following:boolean, followers_count?, following_count?
  Follow toggle must return updated counts for BOTH follower_count and following_count of current user AND target if possible.

fandoms store
  Listing endpoints: /api/fandoms, /trending, /search, /:idOrHandle, /:idOrHandle/posts, /:idOrHandle/members
  Fandom shape must include: id, name, handle, description?, cover_image_url?, logo_url?, members_count, posts_count, is_member:boolean, role?:"member"|"moderator"|"admin"|"owner"
  Join toggle: Return { is_member, members_count }
  Role update: Return user id + new role
  Hashtags: list of { hashtag, uses }

search store
  Global search: Provide arrays only for types returned. Do not return huge payloads—cap each list (e.g., 5-10 items) for preview; include counts optionally: counts:{ posts, fandoms, users, products }
  Suggestions: { query, suggestions:[string] }

notifications store
  GET /api/notifications returns: { data:[Notification], meta, unread_count }
  Notification object: { id, type, data (type-specific payload), read:boolean, created_at, read_at:null|timestamp }
  Mark read endpoints must return updated unread_count.

cart store
  Cart GET returns: { items:[CartItem], totals:{ items, subtotal, shipping, total, currency } }
  CartItem required: { id, product:{ id, name, price, currency, images:[url] }, quantity, unit_price, total_price, options? }
  All currency fields numeric (no formatted strings). Provide currency code (e.g., "USD").

products store
  Product list supports filters & sorting. Provide meta.
  Product minimal card: { id, name, price, currency, images:[url], brand, category, rating?, stock }
  Product detail (future): add description (HTML or markdown), attributes, related_products:[id,...]

orders store
  List: { data:[Order], meta }
  Order: { id, status (pending|paid|shipped|completed|cancelled), items:[CartItem], subtotal, shipping, total, currency, created_at }
  Cancel returns updated order with status:"cancelled".

wishlist integration
  Toggle returns { wished:boolean, count (wishlist total items) }

trends store (hashtags)
  trending hashtags: { hashtag, uses, posts_count }

search performance
  Provide server-side limit param; default 10. Support ?page for scrolling results when type specified.

GENERAL BACKEND FIELD RULES
  Always include id on root objects.
  Use snake_case for backend keys (current convention) – frontend maps if needed.
  Date fields ISO8601 ("YYYY-MM-DDTHH:MM:SSZ" preferred) except date_naissance can be date-only (YYYY-MM-DD).
  Numeric counts never as strings.
  Empty collections as [], not null.
  Boolean flags explicitly true/false (never 0/1) for liked, is_member, is_following, read.

ERROR CONTRACT
  Validation (422): { message:"Validation failed", errors:{ field:[msg,...] } }
  Auth expired (401): { message:"Unauthenticated" }
  Permission (403): { message:"Forbidden" }
  Not found (404): { message:"Resource not found" }

FIELD CHANGE POLICY
  If backend must rename/remove a field, expose deprecated field for one release cycle with null + warning header: X-Deprecated-Fields: field1,field2

PERFORMANCE / PAGINATION
  Large list endpoints should allow limit up to 50; default 20.
  meta object required keys: page, limit, total, last_page (ceil(total/limit)).
  Provide ETag or Last-Modified headers for cacheable lists (optional enhancement).

SECURITY
  All modifying endpoints require Authorization header.
  Reject multipart without required content field (return 422).
  Rate limit write actions (posts, comments, likes) – return 429 with { message:"Too many requests" }.

MEDIA HANDLING
  Return fully qualified URLs OR relative paths starting with storage/; no mix of both in same array.
  If upload returns { url }, ensure URL immediately accessible (no processing delay) or include status field.

FEED & POSTS
GET /api/feed/home                  Auth: R  -> { posts:[Post], meta }
GET /api/feed/explore               Auth: O  -> { posts:[Post], meta }
  Explanation:
    Purpose: public "explore" feed to surface discoverable content across the platform. Unlike the authenticated home feed, explore mixes trending, recommended and fresh posts to help users discover new fandoms and creators.

    Auth: optional — if Authorization header present, include user-specific flags (e.g. author.is_following, isLiked) and bias rankings toward user interests when appropriate.

    Query parameters:
      - page (int) — default 1
      - limit (int) — default 20, max 50 recommended
      - q (string) — optional keyword search/filter
      - fandom_id (int) — optional filter by fandom
      - sort (string) — e.g. newest | trending | relevance
      - tags (csv) — optional tag filtering
      - cursor (string) — optional cursor token (if cursor pagination used)

    Response (200):
      {
        "posts": [ /* Post objects per contract */ ],
        "meta": { "page":1, "limit":20, "total":400, "last_page":20 }  // meta recommended
      }

    Ranking / personalization guidelines:
      - Unauthenticated: prioritize trending and high-engagement posts with freshness decay.
      - Authenticated: blend personalized signals (preferred_categories, follows, past likes) with trending signals.
      - Use deterministic tie-breakers for stable pagination (created_at desc, id).

    Performance & caching:
      - Cache popular explore pages with short TTL (30–120s).
      - Prefer cursor pagination for large datasets to avoid offset penalties.
      - Provide ETag/Last-Modified headers where applicable.

    Edge cases & behavior:
      - Empty results must return { posts: [], meta: { page, limit, total:0, last_page:0 } } not null.
      - Invalid params produce 422 with field errors.
      - Keep response shape consistent (media array shape, ISO dates, numeric counts).

    Frontend expectations:
      - Feed must return author.{id,name,avatar} and post flags (isLiked, trending) when available.
      - Store expects { posts:[Post], meta? } exactly as other feed endpoints.
      - For optimistic interactions (likes/follows) frontend will call dedicated toggles and rely on their responses to update feed entries.

    Testing checklist (suggested):
      - Pagination meta correctness and page boundaries.
      - Auth vs unauth responses (flags present when auth supplied).
      - Sorting stability across pages.
      - Load/latency under expected concurrency and cache hit/miss scenarios.
